# DB 분할

## Partitioning

### 정의 및 특징

테이블을 더 작은 테이블들로 나누는 것

- 성능 향상: 특정 조건의 데이터만 조회하거나 수정할 때 관련 파티션만 접근하므로 I/O 부하가 감소할 수 있습니다.
- 관리 용이성: 파티션 단위로 쿼리를 수행해 관리 복잡도를 줄일 수 있습니다.
- 가용성 향상: 파티션별로 독립적인 백업과 복구가 가능하여 데이터 손실 위험을 최소화합니다.

### 종류

- 수평 파티셔닝(Horizontal Partitioning)
    - 행 기준으로 데이터를 분할하여 각 파티션에 동일한 구조의 데이터를 저장합니다.
    - 범위 파티셔닝: 날짜나 ID 범위에 따라 데이터를 분할할 수 있습니다.
    - 목록 파티셔닝: 명시된 값의 목록에 따라 데이터를 분할합니다. (ex, 국가 코드)
- 수직 파티셔닝(Vertical Partitioning)
    - 열 기준으로 데이터를 분할하여 자주 사용되는 열과 그렇지 않은 열을 분리합니다.
    - 자주 사용하는 열에 대한 접근 속도를 향상시킬 수 있습니다.
- 해시 파티셔닝(Hash Partitioning) (수평)
    - 해시 함수를 사용하여 데이터를 분할합니다.
    - 단점: 특정 데이터가 어느 파티션에 있는지 판단하기 어려울 수 있고, 파티션의 수가 변경되면 해시도 변경될 필요가 있습니다.
    - 장점: 데이터의 균등한 분포를 보장합니다.

## Sharding

### 정의 및 특징

같은 테이블 스키마를 가진 데이터들을 다수의 DB에 분산해서 저장하는 기법 (horizontal partitining 아닌가?)

 -> 각 파티션이 독립된 DB에 저장된다는 차이점이 있습니다.

- **성능 향상:** 읽기 및 쓰기 요청을 여러 인스턴스에 분산 처리하여 전체 시스템의 처리량을 높입니다.
- **확장성:** 데이터와 트래픽이 증가함에 따라 수평적 확장이 가능합니다.
- **고가용성:** 한 샤드에 장애가 발생하더라도 다른 샤드는 독립적으로 운영되어 전체 시스템으로 전파되지 않습니다.

### 종류

- 범위 샤딩(Range Sharding) = 범위 파티셔닝
- 해시 샤딩(Hash Sharding) = 해시 파티셔닝
- 지리적 샤딩(Geographic Sharding)
    - 특정 지역의 사용자 데이터를 해당 지역의 서버에 저장하여 지연 시간을 최소화합니다.

## Replication

### 정의 및 특징

여러 개의 DB를 Master - Slave(Primary - Secondary)구조로 구축

통상적으로 Master에서 쓰기를, Slave에서 읽기 작업을 수행합니다. (꼭 그런건 아닙니다)

쓰기 노드(Master)에서 변경된 데이터를 읽기 노드(Slave)로 전파하여 데이터 일관성을 유지합니다.

- 데이터 가용성: 하나의 서버에 장애가 발생하더라도 다른 복제본을 통해 데이터 접근이 가능합니다.
- 부하 분산: 읽기 요청을 여러 복제본에 분산시켜 읽기 성능을 향상시킬 수 있습니다.

### 종류

- 동기 레플리케이션(Synchronous Replication)
    - 마스터 서버에서 데이터 변경 시 종속 서버에도 즉시 반영되며, 모든 서버가 동일한 데이터를 유지합니다.
- 비동기 레플리케이션(Asynchronous Replication)
    - 마스터 서버에서 데이터 변경 후 일정 시간 후에 종속 서버로 변경 사항이 전파됩니다.
    - 실시간 동기화는 아니지만, 성능 오버헤드가 적습니다.
- 다중 마스터 서버 레플리케이션(Multi-Master Replication)
    - 여러 주 서버에서 동시에 쓰기 작업이 가능하며, 각 서버 간에 변경 사항을 동기화합니다.

### 질문 1. Replication 방식

쓰기 노드, 읽기 노드로 나뉠 때, 
쓰기 노드에서 변경이 발생하면 읽기 노드 쪽으로 푸시하는 방식인지?
아니면 읽기 노드에서 쓰기 노드의 변경을 감지해서 풀 하는 방식인지?

⇒

MySQL 기준으로 설명하겠습니다.
MySQL 복제에서는 기본적으로 쓰기 노드가 변경 사항을 읽기 노드로 전송하는 push 방식이 사용됩니다.

- **구현 방식:**
    1. 슬레이브 서버가 마스터에 연결을 요청
    2. 마스터에서는 해당 연결에 대해 바이너리 로그 덤프 쓰레드를 생성
    3. 이 쓰레드는 마스터의 변경 사항(바이너리 로그 이벤트)을 슬레이브로 전송합니다.

### 질문 2. 그렇다면 데이터 자체를 전송하는지? 아님 변경 사항만 전송하는지?

MySQL 복제에서는 데이터베이스 데이터를 전송하는 것이 아니라, 변경 사항에 대한 이벤트를 기록한 바이너리 로그를 전송합니다. 
이를 통해 슬레이브는 변경된 부분만을 반영하여 데이터 일관성을 유지할 수 있습니다.

이때 변경 사항을 넘기는 방법은 다음과 같이 나뉩니다.

1. Statement-Based Replication
    - SQL문 자체를 바이너리 로그에 작성
    - 장점
        - 검증된 기술: 오랜 기간 사용되어 왔으며 안정성이 입증
        - 저장 공간 효율: 동일한 변경을 하나의 SQL 문으로 기록하므로 로그 크기가 작아짐
        - 감사 기능 활용: 로그에 실제 실행한 SQL 문이 포함되어 있어 감사(audit) 목적으로 유용
    - 단점
        - 비결정적 함수 문제: NOW(), RAND(), UUID() 등 비결정적 함수나 저장된 프로그램에 의존하면 소스와 복제본 간 불일치가 발생
        - 잠금 및 동시성 이슈: 복제 시 전체 명령문이 평가되어야 하므로, 명령문에 따라 더 많은 행 잠금이 필요해 동시성이 떨어질 수 있음.
        - 오류 확산 위험: 복잡한 명령문의 경우 시간이 지남에 따라 복제본에서 점차 오류가 누적 가능
2. Row-Based Replication (디폴트)
    - 개별 테이블 행이 어떻게 변경되는지를 나타내는 이벤트를 바이너리 로그에 기록
    - 장점
        - 비결정적 함수 문제 해결**:** 모든 변경된 행의 실제 데이터만 복제하므로, 비결정적 함수 사용 시에도 소스와 복제본이 정확하게 일치
        - **세밀한 변경 적용:** 변경이 발생한 행만 수정하기 때문에, 전체 SQL 문을 다시 실행하지 않아도 되어 복제 정확성이 높음
    - 단점
        - **로그 용량 증가:** 변경된 각 행의 데이터를 기록하므로, 많은 행이 변경될 경우 바이너리 로그의 크기가 크게 증가할 수 있음.
        - **백업/복원 시간 지연:** 로그 데이터가 많아짐에 따라 백업과 복원 작업에 더 오랜 시간이 소요될 수 있음
3. Mixed Replication
    - 혼합 방식
    = Statement-Based Replication으로 실행 중에 실행하지 못하는 상황에 자동 전환

### 질문 3. 바이너리 로그 덤프 쓰레드는 네트워크를 통해 물리적으로 분리된 다른 DB와도 통신이 가능한가?

바이너리 로그 덤프 쓰레드는 단순히 로컬에서만 동작하는 것이 아니라, 네트워크를 통해 다른 기기(슬레이브 서버)와 연결되어 데이터를 전송하는 방식으로 동작합니다.

- **네트워크 기반 복제:**

    슬레이브 서버가 마스터 서버에 접속을 요청하면, 마스터는 해당 연결을 이용해 바이너리 로그 덤프 쓰레드를 생성합니다. 
    이 쓰레드는 마스터의 변경 이벤트(바이너리 로그 이벤트)를 네트워크를 통해 슬레이브로 전송합니다.
    따라서, 레플리케이션 환경에서는 마스터와 슬레이브가 네트워크를 통해 연결되어 있어야 하며, 바이너리 로그 덤프 쓰레드는 그 연결을 활용해 변경 사항을 전파하는 역할을 합니다.
    이때, MySQL 고유의 프로토콜을 기반으로 한 TCP 연결을 사용합니다.

- TCP 연결:
    
    슬레이브가 마스터에 접속할 때 기본적으로 MySQL의 기본 포트(보통 3306)를 통해 TCP 연결이 이루어집니다.
    
- MySQL 프로토콜:
    
    이 연결은 MySQL의 네이티브 프로토콜을 사용하여 바이너리 로그 이벤트와 관련 데이터를 주고받습니다. HTTP 프로토콜과 달리, MySQL 프로토콜은 데이터베이스 작업에 특화되어 있으며, 복제에 필요한 고성능 및 안정성을 제공합니다.
    

추가적으로 MySQL 복제는 MySQL 클라이언트/서버 프로토콜(TCP 기반)을 사용하여 직접 연결을 맺고 데이터를 전송하므로, Kafka나 Redis의 pub/sub 같은 별도의 메시징 시스템이 필요하지 않습니다.
