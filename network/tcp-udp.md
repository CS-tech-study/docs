## TCP

- OSI 7계층 모델 중 4계층(TCP/IP 모델 전송계층)에서 사용

![image.png](/network/images/tcp.png)

### 특징

- **연결 지향적 통신**
    
    데이터를 전송하기 전, 3-way handshake를 거쳐 안정적인 논리적 세션을 수립합니다.
    
    데이터 전송 후에는 4-way handshake 과정을 통해 해제합니다.
    
- **신뢰성 있는 전송**
    
    오류제어, 혼잡 제어 등의 기능을 수행합니다.
    
    - 각 패킷에는 시퀀스 번호와 ACK(응답) 번호가 부여되어 도착 순서와 누락 여부를 확인할 수 있습니다.
    - 오류 발생 시 재전송을 요청함으로써 데이터의 완전성을 유지합니다.
- **헤더의 복잡성**
    
    TCP 헤더에는 포트 번호, 시퀀스 번호, ACK, 윈도우 크기, 체크섬 등 다양한 제어 정보가 포함되어 있어, 연결의 상태 및 데이터 전송의 흐름을 관리할 수 있습니다.
    
- **적용 분야**
    
    파일 전송 등 신뢰성과 데이터 순서 보장이 중요한 서비스에서 주로 사용됩니다.
    

## UDP

- OSI 7계층 모델 중 4계층(TCP/IP 모델 전송계층)에서 사용

![image.png](/network/images/udp.png)

### 특징

- **비연결형 통신**
    
    UDP는 별도의 연결 설정 없이 데이터를 전송합니다.
    
- **신뢰성 미보장**
    
    UDP는 오류 복구나 재전송 기능이 없으므로, 패킷 손실이나 순서 뒤바뀜이 발생할 수 있습니다.
    
- **경량화된 헤더**
    
    UDP 헤더는 포트 번호, 데이터 길이, 체크섬 등 최소한의 정보만 포함하여, 처리 오버헤드가 매우 낮습니다.
    
    이로 인해 빠른 데이터 전송이 가능하지만, 데이터의 순서나 완전성이 보장되지 않습니다.
    
- **적용 분야**
    
    실시간 스트리밍, 온라인 게임 등 약간의 데이터 손실이 허용되지만 지연이 최소화되어야 하는 서비스에 적합합니다.

## TCP 연결에 여러 스트림 존재한다는 것은?

### Stream

HTTP/2에서는 HTTP1.1에서의 message라는 단위외에 frame, stream 이라는 단위가 추가 되었습니다.

- Frame: HTTP/2 통신상의 제일 작은 정보의 단위, (Header or Data)
- Message: H1.1과 마찬가지로 요청 혹은 응답의 단위, 다수의 Frame으로 구성
- Stream: 클라이언트와 서버 사이에 맺어진 연결을 통해 양방향으로 주고받는 하나 이상의 Message.

즉, Frame → Message → Stream 의 구조로, 각 스트림은 독립적인 메시지 흐름을 담당합니다.

![image.png](/network/images/stream.png)

HTTP1.1에서는 요청과 응답은 각각 하나의 메시지가 하나의 오브젝트의 요청과 응답을 담당하였습니다.

HTTP/2에서는 스트림 하나가 다수개의 요청하고, 이에 대한 다수개의 응답 정보를 포함하고 있는 구조로 바뀐것 입니다.

## HTTP/3는 UDP 기반인데 어떻게 패킷 손실을 감지하는가

그 이유는 UDP 기반의 QUIC를 사용하기 때문입니다.

### QUIC

#### 도입

HTTPS 프로토콜은 TCP/IP와 TLS레이어가 나누어져 있어서 불필요한 라운드 트립 딜레이(RTT)가 발생한다는 문제가 있습니다.

![image.png](/network/images/quic.png)

그래서 이 불필요한 2번의 RTT를 한번으로 줄이기 위해 도입된 것이 QUIC입니다.

#### 지원 기능

QUIC은 UDP 위에 TCP 프로토콜의 흐름 제어, 오류 제어, 혼잡 제어와 SPDY의 스트림 멀티플렉싱 기능이 모두 구현되어 있습니다. 

![image.png](/network/images/quic-tcp.png)

#### 패킷 손실 감지 

TCP/IP는 패킷을 재전송할 때 시퀀스 번호를 동일한 값을 주기 때문에, 서버가 보내준 ACK가 어떤 요청에 대해서 보내준 건지 판단할 수 없는 문제가 발생합니다. (retransmission ambiguity)

QUIC은 재전송 패킷도 새로운 번호를 부여하도록해서 이 모호성 문제를 해결합니다. 

또한 클라이언트의 RTT계산을 돕기 위해, 서버에서 요청을 수행하는데 걸린 시간을 첨부해서 응답합니다.

TCP/IP보다 더욱 정확한 RTT 계산방식으로 인해 불필요한 패킷 재전송을 방지했습니다.
