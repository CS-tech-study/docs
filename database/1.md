## 포그라운드 스레드 (클라이언트 스레드)

클라이언트의 요청을 처리해줄 스레드로 MySQL 서버에 접속된 클라이언트의 수만큼 존재, 주로 쿼리 문장을 처리,

클라이언트가 작업을 마치고 커넥션을 종료하면 다시 스레드 풀(ThreadPool)로 돌아감

## 백그라운드 스레드

## 트랜잭션이 길어지면 안되는 이유
- 언두 로그에서 관리되는 이전 데이터(스냅샷)가 삭제되지 못하고 오랫동안 관리되어야 함
- 락을 오래 잡게 되므로 성능이 떨어지고 데드락 발생 가능성이 올라감

## **MVCC(Multi-Version Concurrency Control)**

락을 사용하지 않고도 **읽관된 읽기 (consistent read)** 를 보장하는 동시성 제어 기법

InnoDB의 디폴트 트랜잭션 격리 수준인 REPEATABLE READ 혹은 그보다 낮은 수준의 격리 수준을 사용하면 select로 조회 시 s-lock을 사용하지 않고 조회하는데, 이렇게 s-lock 없이도 읽기의 일관성을 유지할 수 있는 이유가 MVCC의 스냅샷 때문
>첫 조회 시점에 **스냅샷을 만들고 다음번에 동일한 데이터를 읽을 때는 이 스냅샷을 읽는 방식으로 구현

다만 락을 획득하는 구문은(ex. `INSERT`, `DELETE`, `UPDATE`, `SELECT FOR UPDATE`) 스냅샷이 아닌 가장 최근의 커밋된 상태를 사용하기 때문에 락을 획득하지 않는 일반 `SELECT`와 함께 사용하면 읽기 작업의 일관성이 깨질 수 있음
### 클러스터링 인덱스

인덱스의 키가 실제 테이블의 정렬 기준

>InnoDB의 모든 테이블은 기본적으로 **프라이머리 키를 기준으로 클러스터링**(PK값 순서대로 디스크에 저장), 모든 세컨더리 인덱스는 레코드의 주소 대신 **PK 값을 논리적 주소로 사용**

리프 노드에 레코드 자체가 저장되어 있으므로 추가 랜덤 I/O가 발생하지 않으므로 더 빠른 검색

##  인덱스 성능에 영향을 미치는 요소

- 인덱스 키 값의 크기
	인덱스 키의 크기가 클수록 동일한 페이지(또는 블록)에 저장할 수 있는 키의 개수가 줄어들어 인덱스 트리의 높이가 증가할 수 있고, 디스크로부터 페이지를 읽어야 하는 횟수가 증가할 수 있음

- 카디널리티: 모든 인덱스 키 값 중 유니크한 값의 수
	카디널리티가 낮은 칼럼에 대해 인덱스를 걸면 인덱스 조회 후에도 많은 레코드를 다시 읽어야 하므로 비효율적


일반적으로 옵티마이저는 인덱스를 통해 레코드 1건을 읽는 것이 테이블에서 직접 레코드 1건을 읽는 것보다 4~5배 정도 비용이 더 많이 드는 작업인 것으로 예측하기 때문에, 

읽어야 할 레코드의 건수가 전체 테이블의 20~25%를 넘어가면 인덱스를 사용하지 않고 테이블 풀 스캔을 한다고 함

예를 들어 직접 레코드를 읽는건 순차적 IO로 1ms가 걸리고, 인덱스로 레코드를 찾는건 B+-tree의 리프 노드까지 도달하는데 걸리는 시간과 랜덤 IO로 인해 5ms이 걸린다고 하면

1000개의 레코드가 있는 테이블에서 1개의 레코드만 찾는 상황이라면 당연히 인덱스를 사용해서 찾는게 빠르겠지만, 

한 200개 정도 레코드를 찾아야 하는 상황이라면 이때부턴 테이블 풀 스캔에 걸리는 시간도 1000ms, 인덱스 사용에 걸리는 시간도 1000ms 이므로 200개 이상부터는 테이블 풀 스캔을 사용하는 것이 나음

>그렇다면 직접 디스크에서 데이터를 가져오기 전에 옵티마이저가 레코드를 몇개 정도 가져올 지 어떻게 예상하느냐가 문제인데...다음 주에 찾아보겠습니다

### 커버링 인덱스

쿼리에서 필요한 모든 데이터가 인덱스에 포함되어 있어, 테이블의 실제 데이터 블록에 접근하지 않고도 원하는 정보를 얻을 수 있는 인덱스

```SQL
CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    first_name VARCHAR(50),
    last_name VARCHAR(50),
    department_id INT,
    salary DECIMAL(10, 2)
);

SELECT employee_id, first_name
FROM employees
WHERE department_id = 10;

CREATE INDEX idx_department_employee
ON employees (department_id, employee_id, first_name);
```

이렇게 인덱스를 만들면 인덱스의 키에 쿼리에 필요한 모든 데이터가 이미 다 있으므로 실제 데이터를 랜덤IO로 찾아갈 필요가 없으므로 더 빠른 조회 가능
