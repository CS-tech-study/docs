## MySQL 옵티마이저 

쿼리를 처리하기 위한 여러가지 가능한 방법을 만들고, 각 단위 작업의 비용(부하) 정보와 대상 테이블의 예측된 **통계 정보**를 이용해 
실행 계획 별 비용 산출 -> 이 중 **최소 비용이 예상되는 실행 계획을 선택하여 쿼리 실행**

## 옵티마이저는 레코드를 몇개 정도 가져올 지 어떻게 예상하는가?

다시 말하면 **조건절에 일치하는 레코드 건수가 어느정도인지 어떻게 예측하는가?**
## 통계 정보

```SQL
use mysql;
select * from innodb_index_stats;
select * from innodb_table_stats;
```

테이블 통계 칼럼

- database_name : 데이터베이스 네임  
- table_name : 테이블 이름 ,파티션 이름 또는 서브 파티션  
- last_update : 이 행을 마지막으로 업데이트한 시간을 나타내는 시간  
- n_rows : 테이블의 전체 레코드 수  
- clustered_index_size : Primary Key 의 크기(InnoDB 페이지 개수)  
- sum_of_other_index_sizes : PK를 제외한 인덱스의 크기(InnoDB 페이지 개수)

인덱스 통계 칼럼

- 'n_diff_pfx%' : 인덱스가 가진 유니크한 값의 개수 (카디널리티) 
- 'n_leaf_page' : 인덱스 리프 노드의 페이지 수  
- size : 인덱스 트리에 전체 페이지수

> 통계정보가 업데이트 되지 않으면 정확한 row수나 인덱스 정보가 반영되지 않는다.

## 히스토그램

통계 정보로 테이블의 전체 레코드 건 수와 인덱스된 칼럼이 가지는 유니크한 값의 개수 정도만 있기 때문에 옵티마이저는 데이터가 균등하게 분포되어 있을 것으로 예측하여 레코드 수를 예상
>예를 들어 테이블에 레코드가 1000건 있고 인덱스된 특정 칼럼의 카디널리티가 100이면 이 칼럼을 통해 조회할 때 대략 10개의 레코드가 일치할 것으로 예상

그러나 실제 데이터는 항상 균등한 분포도를 가지지 않기 때문에 부정확하고, 이를 해결하기 위해 각 범위(버킷) 별로 쪼개서 레코드의 건수와 유니크 한 값의 개수(카디널리티)를 수집하여 저장한 것이 히스토그램

주로 인덱스되지 않은 칼럼에 대한 데이터 분포도를 참조하는 데 사용
> 인덱스된 칼럼을 검색 조건으로 사용하는 경우엔 히스토그램을 사용하는 것보다 Index Dive로 직접 수집한 정보를 사용하는게 더 정확하기 때문

## Index Dive

조건절에 일치하는 레코드 건수를 예측하기 위해 실제 인덱스를 샘플링해서 살펴보는 과정
> B-Tree 구조를 따라가면서 범위의 시작점과 끝점을 찾아내어 해당 범위 내의 레코드 수를 추정

일반적으로는 높은 CPU나 Disk 리소스를 소모하지 않지만, 다음과 같은 경우에선 상황이 달라질 수 있다.

- 많은 개수의 엘리멘트가 `IN (list)`에 사용되는 경우
- `IN (list)` 조건 자체가 여러 번 사용되는 경우
- `IN (list)` 조건들이 사용할 수 있는 인덱스가 많은 경우

인덱스가 많으면 실행 계획 비용이 높아질 수 있는 이유는 
MySQL 서버를 포함한 모든 RDBMS에서는 쿼리가 실행되면, 해당 쿼리의 최적 실행 경로를 찾기 위해
**사용 가능한 모든 처리 방법**의 예상 비용을 계산하는데, 
테이블의 **인덱스가 많으면 많을수록 사용 가능한 방법이 많아지게 되면서 실행 계획 수립 과정이 복잡해진다.**

Index Dive 비용이 너무 크다면 옵티마이저 힌트를 사용하여 실행 계획 수립 단계를 줄여야 함
1. `FORCE INDEX (ix_userid_categoryid)`
2. `USE INDEX (ix_userid_categoryid)`
3. SELECT `/*+ INDEX (articles ix_userid_categoryid) */`

솔직히 이정도면 DBA의 영역인거같아서 깊게 이해할 필요는 없을거같고...자세한 내용이 궁금하면 당근 블로그 [Index Dive 비용 최적화](https://medium.com/daangn/index-dive-%EB%B9%84%EC%9A%A9-%EC%B5%9C%EC%A0%81%ED%99%94-1a50478f7df8) 참고..

## 번외

## 인덱스를 사용하지 않고 풀 테이블 스캔을 하는 경우

일반적으로는 인덱스는 테이블의 2~3개 칼럼만으로 구성되기 때문에 테이블 자체보다는 용량이 작아서 디스크 읽기를 줄일 수 있으므로 훨씬 빠른 조회가 가능하지만, 다음과 같은 경우에는 인덱스를 사용하지 않고 풀 테이블 스캔을 한다.

- 테이블 페이지가 1개로 구성된 경우 인덱스가 걸려 있어도 인덱스를 통해 읽는것보다 풀 테이블 스캔하는 것이 빠르므로 풀 테이블 스캔 수행 (쿼리 성능을 추정할 때 더미 데이터를 넣어야 하는 이유)
- `WHERE`절이나 `ON`절에 인덱스를 이용할 수 있는 적절한 조건이 없는 경우
- 인덱스 레인지 스캔을 사용할 수 있는 조건 일치 레코드 건 수가 너무 많다고 옵티마이저가 판단하는 경우 (B-tree를 샘플링해서 조사한 통계 정보를 사용)

InnoDB의 경우 풀 테이블 스캔을 할 때 처음 몇개의 페이지는 포그라운드 스레드에서 읽지만 특정 개수만큼 연속된 페이지가 읽히면 read ahead 방식으로 페이지를 미리 디스크에서 읽어서 버퍼 풀에 캐시

## ORDER BY 사용 시 주의사항

인덱스가 있다면 이미 해당 칼럼에 대해 정렬되어 있으므로 추가적인 정렬 작업이 필요하지 않음
반면 인덱스가 없다면 ORDER BY 사용 시 정렬을 해줘야 하므로 소트 버퍼 사용

ORDER BY나 GROUP BY 같은 작업은 LIMIT 건수만큼 가져와서는 처리할 수 없으므로 LIMIT이 있더라도 일단 조건을 만족하는 레코드를 모두 가져온 후 정렬을 수행하거나 그루핑 작업을 실행한 후에서야 LIMIT으로 건수를 제한할 수 있으므로 큰 성능 향상이 일어나지 않을 수 있음
>쿼리를 스트리밍 방식으로 처리하지 못하고 버퍼링 방식으로 처리해야 함

따라서 **ORDER BY를 사용할거면 웬만하면 인덱스를 걸어주는 게 좋음, 특히 LIMIT 과 함께 사용할 것이라면**
